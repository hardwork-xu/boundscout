## 开场：问题与有价值的结果

BoundScout 研究一个小型 CPU 精确向量索引何时能抵消自身的构建与查询成本。使用场景是一组固定本地特征向量，以及重复的 top-k 查询。如果包围盒计算、排序或 Python 候选维护开销超过节省的距离计算，仅报告距离计算减少会产生误导。因此，项目公开工作量计数，保留编译实现的穷举基线，并记录不利情况。

最有用的结果有明确范围：在预先指定的 32,768 个点、32 维聚类场景中，相比更强的 `cdist-4096` 扫描快 3.50–3.62 倍，但 `cKDTree` 仍比 BoundScout 快 2.01–2.71 倍。在归一化的真实 GloVe25 数据上，BoundScout 比两者都慢。项目贡献是可检查的实现和可复现的比较，不是新的最近邻算法。

## 一次查询如何执行

构建时选择跨度最大的坐标轴，按中位数划分点集，将叶节点整理为连续块，并保存每块逐坐标的最小值和最大值。存储顺序虽然变化，原始行 ID 仍然保留。

对于查询 q 和块包围盒 [l,u]，到包围盒的平方距离为

$$
L_B(q)=\sum_j \max(l_j-q_j,\;0,\;q_j-u_j)^2.
$$

在实数运算中，它不会大于到块内任意点的平方距离。查询按下界从小到大访问块；已有 k 个候选后，如果剩余最小下界严格大于当前最差候选的平方距离，就可以停止。等号不能剪掉，因为等距点可能有更小的原始 ID。候选选择保留边界并列点，最终按 `(计算所得平方距离, 原始行 ID)` 排序。

实现使用 float64 坐标差和 SciPy 编译平方距离核。下界乘以 `1 - 64 * eps * (D + 1)`，再向下移动一个可表示值并截断到零；停止阈值向上移动一个可表示值。保守余量与对抗性测试为所声明的计算距离契约提供支持，但不构成任意接近输入在精确实数意义下排序的形式化证明。参见 [`engine.py`](../../src/boundscout/engine.py) 和[数值契约](ARCHITECTURE.md#数值契约)。

## 工程取舍

将叶节点展开为块有助于检查实现，但每次查询都要支付全部包围盒下界和排序的开销。包围盒分离度差时，所有点可能仍需计算。存储数组占用 O(ND + N + BD) 空间；构建副本、验证和候选维护需要额外临时内存。`max_bytes` 限制索引逻辑数组大小，而不是进程 RSS。

主要场景的索引逻辑数组为 **8.31 MiB**；独立新进程测得的峰值为 **122.55–128.48 MiB**，包含导入、数据准备、构建和一次查询批次。两者回答不同的问题。构建耗时 **40.65–46.51 ms**。以构建时间除以相对 `cdist-4096` 的批次节省时间，两个种子都得到约 **两个 64 查询批次**的构建摊销门槛；该估算不包含文件 I/O 或查询分布变化。

[`storage.py`](../../src/boundscout/storage.py) 先在同级临时目录写入数组和元数据，再发布到新索引路径。加载时检查摘要、形状、原始 ID 的完整排列与真实块几何，之后使用只读内存映射。摘要检测相对于清单的内容变化，无法证明作者身份。其他进程仍能修改映射文件。上下文管理器用于释放映射，调用方不能在查询期间关闭索引。[安全说明](../../SECURITY_zh.md) 给出了信任边界。

## 值得详细讲解的实验

冻结矩阵包含六类工作负载、两个种子、六种方法，每种方法预热一次后测量七次。保留按种子随机化的方法执行顺序，以及全部 **504 个计时批次**。硬件为 Apple M1 Pro、16 GiB 内存，使用单原生线程；主机有其他交互负载，没有独占 CPU 或温控保证。**111 项离线测试**覆盖独立直接距离参考、并列、重复点、大偏移、数值限制、并发读取、文件损坏及真实 CLI 子进程。全部 **72 个被测方法组合**通过相应正确性检查；`cKDTree` 比较有序距离，因为等距 ID 顺序不属于其契约。

在 `clustered-primary` 上，两个种子的完整 64 查询批次中位数为：

| 方法 | 种子 20260921 | 种子 20260922 |
| --- | ---: | ---: |
| `cdist-256` | 91.535 ms | 92.389 ms |
| `cdist-4096` | 40.504 ms | 39.464 ms |
| `spatial-pruned` | 11.195 ms | 11.288 ms |
| `ckdtree` | 5.570 ms | 4.160 ms |

BoundScout 的距离计算向量数减少 **92.72–92.74%**，达到冻结协议中的 75% 工作量减少和相对 `cdist-256` 至少 1.50 倍加速目标。相对 `cdist-256` 的 8.18 倍加速，在更大块的扫描基线下变为 3.50–3.62 倍，这揭示了基线循环开销的影响。输入顺序分块在此场景的计算量减少为 **0%**；关闭剪枝同样失去了加速优势。后一消融同时移除了下界计算与排序，因此不能将其解释为只隔离距离核的效果。

## 负面结果与下一个问题

两个 128 维各向同性场景的距离计算向量数均减少 **0%**。在 32,768 点场景中，BoundScout 耗时 **210.03–214.64 ms**，而 `cdist-4096` 为 **97.98–98.49 ms**。该场景的 `cKDTree` 更慢，说明没有一种被测索引在全部情况中胜出。

在归一化的 32,768 点 GloVe25 子集上，只减少了 **1.23–2.28%** 的距离计算。BoundScout 为 **120.73–122.02 ms**，`cdist-4096` 为 **36.00–36.71 ms**，`cKDTree` 为 **26.83–30.72 ms**。合成数据中的簇分离优势没有迁移到这份真实工作负载。在讨论部署或继续优化之前，应先解释这一结果。

下一项有价值的实验是对同一批向量施加正交旋转，并扫描叶块大小，同时保持欧氏距离、输入和基线方法一致。这能检验剪枝收益在多大程度上依赖坐标轴方向和块粒度。它属于后续工作，当前冻结矩阵没有给出其结果。每种方法只有七个计时批次，且使用共享主机，现有证据只能支持所记录环境内的中位数比较，不能支持 p99 或统计显著性结论。
